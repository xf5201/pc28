# PC28 多用户自动化下注系统

基于 Telegram 的 PC28(PC蛋蛋)多用户自动化下注系统。用户通过 **Telegram 控制机器人**完成登录、配置、启停策略;系统使用 **GramJS 用户账号(Session)** 监听开奖数据、按策略自动向下注群发送下注消息,并根据开奖结果自动结算盈亏。

> ⚠️ **免责声明**:本项目仅供学习研究 Telegram Bot / GramJS / 自动化调度技术使用。博彩有风险,请遵守所在地区法律法规,使用者的一切行为与本项目作者无关。

## 系统架构

系统同时使用两个 Telegram 身份,各司其职:

```
┌──────────────┐   面板操作    ┌─────────────────────────────┐
│  控制机器人   │ ←─────────── │          用户               │
│ (Telegraf)   │   面板推送    │  (私聊 Bot 按按钮)          │
└──────┬───────┘              └─────────────────────────────┘
       │ 指令下发 / 状态查询
       ▼
┌─────────────────────────────────────────────────────────────┐
│                    Node.js 主进程 (pm2)                      │
│                                                              │
│  ┌──────────┐  ┌───────────┐  ┌──────────┐  ┌────────────┐  │
│  │ Crawler  │→ │ Settlement│→ │ Strategy │→ │ BetSender  │  │
│  │ 抓开奖    │  │ 结算盈亏   │  │ 计算方向  │  │ 发送下注    │  │
│  └──────────┘  └───────────┘  └──────────┘  └─────┬──────┘  │
│       │              │              │             │         │
│  ┌────┴──────────────┴──────────────┴─────────────┴──────┐  │
│  │           SQLite (better-sqlite3, WAL 模式)            │  │
│  └───────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────┘
                                    │
                          ┌─────────▼─────────┐
                          │  TG 用户账号       │
                          │ (GramJS Session)  │────→ 下注群发送 "大 100"
                          └───────────────────┘
```

- **控制机器人(Telegraf Bot)**:只负责与用户交互——面板展示、配置修改、启停策略、报表查询。不直接发下注消息。
- **执行账号(GramJS 用户客户端)**:每个用户登录自己的 TG 账号,Session 持久化在数据库中,启动时自动恢复连接,负责向下注群实际发送下注消息。
- **爬虫(Crawler)**:定时(动态间隔,约 210 秒)从 `pc20.net/api/history` 抓取最新开奖结果,落库后触发结算与下一期下注。

## 功能特性

- **多用户隔离**:每个 Bot 用户绑定自己的执行账号、下注群、策略配置,互不干扰(进程单实例,禁止多实例,避免 Session 冲突)。
- **全流程自动化**:抓开奖 → 结算上期 → 计算下期方向/金额 → 延迟发送到群 → 等待下期开奖结算,循环运转。
- **面板化操作**:Telegram 内联按钮面板,30 秒自动刷新,无需记忆命令。
- **崩溃自恢复**:进程重启后自动恢复 Session、运行中的策略、待结算下注。
- **补录对账结算**:启动时与每轮抓取后,按期号序号(term)自动结算所有历史遗留的未结算注单;停机期间漏抓的开奖按本地缺口自动补录;停机超过数据源回溯窗口(约 24 天)的注单明确撤单并留审计,不永久悬挂。
- **发送自愈**:下注消息发送带 30 秒超时,连接假死自动重建;重连失败会标记账号 ERROR 并自动停策略,面板可见。
- **跳期保护**:策略中断后恢复时,自动清零连挂计数,避免倍投金额严重偏离。
- **代理支持**:设置 `http_proxy` / `HTTP_PROXY` 环境变量后,执行账号自动走 SOCKS5 代理(默认 127.0.0.1:7890)。

## 快速开始

### 环境要求

- Node.js ≥ 18(建议 20+,`better-sqlite3` 需要对应预编译包或本地构建工具)
- pm2(Windows 部署:`npm install -g pm2 pm2-windows-startup`)
- 可直连 Telegram 的网络(或本地 SOCKS5 代理)

### 安装

```bash
git clone https://github.com/xf5201/pc28.git
cd pc28
npm install
```

### 配置

复制 `.env.example` 为 `.env` 并填写:

| 变量 | 说明 | 获取方式 |
|------|------|----------|
| `BOT_TOKEN` | 控制机器人 Token | [@BotFather](https://t.me/BotFather) 创建机器人获得 |
| `TG_API_ID` | TG API ID | [my.telegram.org](https://my.telegram.org) → API development tools |
| `TG_API_HASH` | TG API Hash | 同上 |
| `DATABASE_PATH` | SQLite 数据库路径 | 默认 `./data/database.db` |
| `LOG_LEVEL` | 日志级别 | `info` / `debug` |
| `LOG_DIR` | 日志目录 | 默认 `./logs` |
| `TZ` | 时区 | 默认 `Asia/Shanghai` |

### 启动

```bash
# 生产环境(pm2 守护,配置见 ecosystem.config.js)
pm2 start ecosystem.config.js
pm2 save          # 保存进程列表
pm2 logs pc28-bot # 查看日志

# 开发环境
npm run dev
```

> ⚠️ `ecosystem.config.js` 中 `instances` 必须为 **1**。多实例会导致同一 Session 多处连接冲突。

## 使用流程

在 Telegram 中私聊控制机器人,发送 `/start` 打开主面板,按以下顺序完成初始化:

1. **登录账号**:在主面板点击「登录账号」,按提示依次输入手机号 → 验证码 →(如开启了两步验证)二级密码。登录成功后 Session 自动加密存入数据库,进程重启无需重新登录。
2. **设置下注群**:点击「设定下注群」,输入目标群 ID(如 `-1002751172376`)。**执行账号必须已加入该群且有发言权限**,否则发送会被拒绝并自动停策略。
3. **配置策略**:点击「修改配置」,设置玩法、赔率模式、基础注、倍投比例。(封盘秒数为系统固定值 10 秒,不对用户开放)
4. **启动策略**:回到主面板点击「启动」。此后每期自动循环:上期开奖 → 结算 → 生成下期订单 → 30 秒后发送到群。
5. **查看报表**:随时在面板查看盈亏报表、下注记录、操作日志。

下注消息格式为 `方向 金额`,例如 `大 100`、`小 1`。

## 策略玩法详解

### 基础方向

所有玩法针对开奖号码三数之和的**大小**(SUM ≥ 14 为大,≤ 13 为小)进行,方向取组合方向的第一段(如 `SMALL,EVEN` → 取 `SMALL`)。

### 四种玩法

| 玩法 | 规则 | 开局模式 |
|------|------|----------|
| 顺龙 | 永远跟着上一期开的方向买 | — |
| 反龙 | 永远反着上一期开的方向买 | — |
| **顺2反龙** | 先顺(跟)着买,**每连输 2 把翻转为反**,再连输 2 把翻回顺,循环往复 | 顺(FOLLOW) |
| **反2顺龙** | 先反着买,每连输 2 把翻转一次 | 反(REVERSE) |

- **开局重置**:启动策略或切换玩法时,顺/反模式自动重置回该玩法的开局模式,连挂计数清零(首注金额从基础注重新开始),避免上一局的模式残留导致首注方向不符预期。
- **无历史数据兜底**:数据库中没有任何开奖记录时,首注默认买 `大`。
- **跳期保护**:若本次下注与上次下注之间跨越了期次(说明策略中断过),连挂计数自动清零(保留当前模式),防止倍投金额严重偏离。

### 倍投与结算

- **下注金额**:`基础注 × 倍投比例 ^ 连挂数`,无上限封顶。例如基础注 1、比例 3:1 → 3 → 9 → 27 → 81 …
- **赔率模式**:
  - `2.17`:赢 = 本金 × 1.17;输 = -本金
  - `2.84`:赢 = 本金 × 1.84;输 = -本金
- **回本号码**(`2.84` 模式):豹子(111/222/999)、对子(011/303)、顺子(012/123/324)、13、14 点——押中方向时若开出这些号码按回本处理(盈亏为 0),连挂计数不变;`2.17` 模式仅豹子回本。
- **连挂状态机**(顺2反龙/反2顺龙):回本 → 计数与模式不变;赢 → 计数清零;输 → 计数 +1,且每逢计数为 2 的倍数翻转一次顺/反。

## 下注生命周期

```
CREATED ──(30 秒后发送成功)──→ SENT ──(开奖)──→ SETTLED
   │                              │
   ├──(发送失败/超时)──→ FAILED    └──(开奖)──→ PENDING ──→ SETTLED
   │
   └──(期号已开奖仍未发出)──→ CANCELED(跳期补录)
```

- **CREATED**:订单已生成,等待 30 秒延迟发送。
- **SENT**:已成功发送到下注群(记录 message_id)。
- **FAILED**:发送失败(超时/网络/被限流)。失败后系统自动重建 TG 连接(自愈);若是权限类失败(被踢出群、禁言),立即停止策略并标记账号 ERROR。
- **CANCELED**:期号已开奖但消息仍未发出,由爬虫在下一期开奖时补录取消,不参与结算。
- **SETTLED**:已按开奖结果结算,写入盈亏日志。

每期同一用户仅允许一注(`bot_user_id + period` 唯一),封盘校验在创建订单前进行(距开奖不足 10 秒即跳过该期,固定值不可配置)。

### 补录对账结算

系统停机(尤其停机较久)重启后,会自动完成历史对账:

1. **启动时**:扫描所有 `SENT`/`PENDING` 注单,按期号序号(term)在 `open_results` 中匹配开奖结果,能匹配到的立即结算。匹配用 term 而非完整期号字符串——旧版时区 bug 曾导致同一期在两张表中日期前缀不一致(如 `20261001-3488377` vs `20260930-3488377`),字符串匹配会永久漏结算。
2. **爬虫补空洞**:每轮抓取按本地已有 term 集合判断缺失(而非只看最大期号),停机期间漏掉的开奖(在数据源回溯窗口内,约 10000 期/24 天)自动补录,补录后下一轮对账自动结算对应注单。
3. **超范围撤单**:期号早于数据源最早可补录期的未结算注单,其开奖结果已无法获取,自动撤单(CANCELED)并写入操作日志,避免永久悬挂。

## 性能与并发

大量用户同时使用时的行为分析与已内置的防护措施。

### 并发模型

- **单进程单实例**:better-sqlite3 是同步驱动,所有数据库操作在事件循环内串行执行,**天然无锁、无并发写冲突**——这也是 `instances: 1` 被写死的原因。单实例内不存在数据库层面的并发竞争。
- **WAL 模式** + `busy_timeout 5000ms` + `synchronous NORMAL`:读写互不阻塞日志文件,偶发的外部工具(如 CLI 手工查库)并发访问也不会报锁错误。
- **真正的并发瓶颈在 Telegram API**,不在数据库:面板推送、下注发送都受 TG 速率限制(约 30 消息/秒)约束。

### 数据量增长与查询成本

`open_results`(约 410 期/天)与 `bet_records` 会持续增长,系统对此的防护:

| 措施 | 说明 |
|------|------|
| term 表达式索引 | `idx_open_results_term`(`migrations/002`)让爬虫每轮的补录对账查询(`getMaxTerm`/`getAllTerms`/`getByTerm`)全部走索引扫描,耗时**不随表增长**;`EXPLAIN QUERY PLAN` 确认为 `USING COVERING INDEX` |
| 下界过滤 | 补录缺失判断只查数据源窗口内(约 24 天)的 term,结果集大小恒定 |
| 保留策略 | 爬虫每 6 小时清理超过 35 天的开奖记录(35 天 > 数据源 24 天回溯窗口,不误删可补录数据),`open_results` 稳定在约 1.5 万行 |
| 待结算查询走既有索引 | `bet_records` 的 SENT/PENDING/CREATED 记录极少,按 `idx_bet_records_settle (status, period)` 前缀命中,历史注单再多也不参与扫描 |
| 面板刷新防重叠 | 30 秒仪表盘刷新带运行闸门,用户多导致单轮超时时自动跳过下一拍,推送不堆积、不触发 TG 限流 |
| `bet_records`/`profit_logs` 永久保留 | 这是账本,不自动清理;查询均为用户维度或状态维度索引命中,不随总量增长变慢 |

### 规模评估

- **几十个用户**(当前设计目标):无压力。每期 210 秒的工作量为:1 次抓取 + N 次结算(每用户 1 条,单条事务 < 1ms)+ N 次下注发送,全部索引命中。
- **数百用户**:数据库仍无压力,瓶颈转移到 TG 发送速率——多用户同一瞬间发单会排队,建议届时将发送延迟按用户错开(现状 30 秒固定延迟,单用户场景无影响)。
- **数千用户**:需将 SQLite 换为 PostgreSQL/MySQL(数据库层已用 DAO 隔离,替换成本可控),并把下注发送改为独立进程队列。

## 常见问题排查

### 群里收不到下注,但面板显示"在运行"

按以下顺序排查(这也是实际发生过的事故):

1. **看下注记录状态**:状态是 `CANCELED` 且原因为"跳期补录:期号已开奖,未发送" → 说明发送环节出了问题。
2. **看日志有无成功记录**:每单发送会有两条日志——`发送下注`(开始)和 `下注已发送`(成功)。只有前者没有后者,且没有失败日志,说明 `sendMessage` 挂起。
3. **看 GramJS 连接日志**:`pm2-out.log` 中若出现 `connection closed` → 连续 `WebSocket connection failed` → `Handling reconnect!` 后再无任何连接日志,即为连接假死(GramJS 重连耗尽后卡住,后续请求永久挂起)。
4. **验证 Session 是否仍有效**(只读检测,不发消息):

   ```bash
   node -e "require('dotenv').config();
   const db = require('better-sqlite3')('data/database.db', {readonly:true});
   const a = db.prepare('SELECT session_string FROM accounts LIMIT 1').get();
   const { TelegramClient } = require('telegram');
   const { StringSession } = require('telegram/sessions');
   const c = new TelegramClient(new StringSession(a.session_string),
     Number(process.env.TG_API_ID), process.env.TG_API_HASH, {});
   c.connect().then(async () => { console.log('OK:', (await c.getMe()).id); process.exit(0); })
     .catch(e => { console.log('FAIL:', e.message); process.exit(1); });"
   ```

   若能连上,说明网络和 Session 没问题,是进程内旧客户端假死 → `pm2 restart pc28-bot` 即可恢复。

**已内置的防护**(2026-10-05 修复):发送带 30 秒超时,超时按 FAILED 处理并自动重建连接;重建失败会标记账号 ERROR 并自动停策略,面板可见。

### 首注方向和预期不符

顺2反龙开局应为**顺**(跟上一期方向)。若发现首注反着开,说明当前数据库 `strategy_config.current_direction` 残留了旧模式——**在面板上停止再重新启动策略**(或重新选择一次玩法)即可,系统会自动重置回开局模式并清零连挂。(2026-10-05 已修复:启动/切换玩法时自动重置。)

### 其他

| 现象 | 原因与处理 |
|------|------------|
| 登录时收不到验证码 | 确认手机号格式含国家码(如 `+86…`);TG 会把验证码发到已登录该账号的设备 |
| 发送报 Forbidden | 执行账号被移出下注群或被禁言,系统已自动停策略;重新入群后重启策略 |
| 爬虫报 `fetch failed` | 数据源 `pc20.net` 临时不可达,系统会按动态间隔自动重试,无需处理 |
| 策略启动报"账号状态异常" | 账号状态为 ERROR,在面板重新登录或检查下注群配置 |
